# nimforest

A library for building dependency trees across folders containing Nim projects.

---

## Nim Project File Reference

A Nim project may contain several configuration and dependency files, each serving a distinct role. Understanding how they relate is essential for correct dependency resolution.

---

### `.nim`

**What it is:** A Nim source file. The primary unit of code in any Nim project.

**What it contains:**
- Nim code: type definitions, procedures, macros, constants
- `import`, `include`, and `from ... import` statements that express dependencies on other modules

**How it is used:** The Nim compiler takes one or more `.nim` files as entry points and recursively resolves their imports. Each `import foo` statement is resolved to a `.nim` file on the search path. This file is what nimforest parses to build the intra-project dependency graph.

**How it relates to other files:** `.nim` files are the nodes in the dependency graph. The edges are the `import` statements between them. All configuration files (`nim.cfg`, `config.nims`, `.nims`) exist to influence how `.nim` files are compiled. All Nimble files (`.nimble`, `nimble.lock`, `nimble.paths`) exist to ensure the right `.nim` files from external packages are available on the search path.

**Scope:** One file per module; a package typically contains many.

---

### `.nimble`

**What it is:** The primary package manifest for a Nim project, analogous to `package.json` or `Cargo.toml`.

**What it contains:**
- Package metadata: `name`, `version`, `author`, `description`, `license`
- Nim version constraint: `requires "nim >= 2.0.0"`
- Package dependencies: `requires "packageName >= x.y.z"`
- Entry point(s): `bin` and `srcDir` fields
- Optional task definitions written in NimScript (`.nimble` files are executed as NimScript)

**How it is used:** Nimble (the Nim package manager) reads this file to install dependencies, build the package, and run tasks. The `requires` directives specify which packages must be present, but not their exact resolved versions or where they live on disk.

**Scope:** One per package, at the package root.

---

### `nimble.paths`

**What it is:** A generated file that records the on-disk paths of all resolved dependencies.

**What it contains:**
A plain-text file of compiler flags, one per line (sourced from `nimble/src/nimble.nim`):
```
--noNimblePath
--path:/absolute/path/to/package1
--path:/absolute/path/to/package2
```
The leading `--noNimblePath` clears Nimble's default search paths before adding the explicit resolved ones, ensuring the file is fully self-contained.

**How it is used:** Generated by `nimble setup` (via `updatePathsFile()`), and also updated as a side effect of `nimble develop` and `nimble install`. Nim can be pointed at this file (via `--NimblePath` or by including it from a config file) so it knows where to find each package's source without a registry lookup at compile time.

**How it relates to `.nimble`:** Where `.nimble` declares *what* is needed, `nimble.paths` records *where* the resolved packages actually live.

**Scope:** Generated per project; not usually committed to version control unless using a reproducible-build workflow.

---

### `nimble.lock`

**What it is:** A lockfile that pins the exact version and source of every dependency (direct and transitive) in the dependency graph.

**What it contains:**
- A JSON or structured record of each dependency: name, version, VCS URL, and commit hash.
- Checksums or other integrity data.

**How it is used:** When present, `nimble install` uses the lockfile to reproduce an exact dependency set regardless of what newer versions may have been released. This makes builds reproducible and prevents "works on my machine" version drift.

**How it relates to `.nimble`:** The `.nimble` file expresses version *ranges*; `nimble.lock` collapses those ranges to a single pinned version. The lockfile is derived from the `.nimble` file but is more specific.

**How it relates to `nimble.paths`:** The lockfile pins *which* versions to use; `nimble.paths` tells the compiler *where* those versions are on disk.

**Scope:** One per project; typically committed to version control.

---

### `nimble.develop`

**What it is:** A generated file that records local package checkouts being actively developed alongside the current project.

**What it contains:**
A JSON file with three keys (sourced from `nimble/src/nimblepkg/developfile.nim`):
```json
{
  "version": 1,
  "includes": ["path/to/other/develop/file"],
  "dependencies": ["/absolute/path/to/local/package"]
}
```
- `version` — always `1` (the current schema version)
- `includes` — paths to other `nimble.develop` files to merge in, allowing monorepo-style composition
- `dependencies` — absolute paths to local package directories

**How it is used:** Created when you run `nimble develop` inside a dependency's directory or `nimble develop packageName` from the dependent project. When Nimble resolves dependencies, develop packages are resolved first and any matching installed packages are filtered out — develop entries win unconditionally (sourced from `nimble/src/nimble.nim`, the `initPkgList` procedure).

**How it relates to `nimble.lock`:** `nimble.develop` takes precedence over the lockfile for packages it lists. A package in `nimble.develop` is always resolved to the local path, regardless of what version `nimble.lock` pins.

**How it relates to `nimble.paths`:** After resolution, the local paths from `nimble.develop` are included in `nimble.paths` alongside the cached packages, so the compiler finds them correctly.

**Scope:** Per-project; typically excluded from version control (the local path is machine-specific).

---

### `nim.cfg`

**What it is:** A compiler configuration file written in Nim's configuration file syntax (not NimScript).

**What it contains:**
- Compiler flags: `--opt:speed`, `--threads:on`, `--define:ssl`
- Path additions: `--path:"./src"`
- Conditional sections: `@if windows: ... @end`
- Any option that could be passed to the `nim` compiler on the command line

**How it is used:** The Nim compiler searches for `nim.cfg` files starting from the directory of the file being compiled, then each parent directory up to the project root, and finally in the Nim installation directory. All found files are merged. This makes it possible to have project-wide settings without modifying the compiler invocation.

**Scope:** Can exist at any directory level; multiple files are merged. Processed before `.nims`/`config.nims`.

---

### `.nims`

**What it is:** A per-file or per-directory NimScript configuration file.

**What it contains:**
- NimScript code (a subset of Nim) that is executed by the compiler as part of configuration
- `switch("define", "myFlag")` calls that set compiler options programmatically
- Arbitrary logic: conditional flags based on OS, architecture, environment variables

**How it is used:** When compiling `foo.nim`, the compiler looks for `foo.nims` in the same directory and executes it. A `.nims` file in a directory acts as a configuration for all `.nim` files in that directory. Because it is NimScript, it is more expressive than `nim.cfg`.

**How it relates to `nim.cfg`:** Both configure the compiler. `nim.cfg` uses a simple key-value/flag syntax and is processed first. `.nims` uses full NimScript and is processed after. They can coexist; `.nims` settings take effect after and can override `nim.cfg`.

**Scope:** Per-file (`foo.nims` alongside `foo.nim`) or per-directory.

---

### `config.nims`

**What it is:** A project-level NimScript configuration file, conventionally placed at the project root.

**What it contains:**
- The same NimScript content as a `.nims` file: `switch(...)` calls, conditional logic, path setup

**How it is used:** The Nim compiler automatically picks up `config.nims` from the project root directory (the directory where compilation is invoked). It applies to all compilations run from that directory. This is the standard place to put project-wide compiler configuration in NimScript form.

**How it relates to `.nims`:** `config.nims` is the project-root-scoped variant. A `.nims` file is scoped to a specific `.nim` file or subdirectory. The compiler processes `config.nims` before per-file `.nims` files.

**How it relates to `nim.cfg`:** `config.nims` is the NimScript equivalent of a project-root `nim.cfg`. The two formats can coexist; `nim.cfg` is processed first, then `config.nims`.

**Scope:** One per project root; typically committed to version control.

## Relationships at a Glance

**Source**
```
.nim          — source files; nodes in the dependency graph
```

**Dependency resolution (Nimble)**
```
.nimble       — declares required packages and version ranges
nimble.lock   — pins exact versions for reproducible builds
nimble.develop — overrides packages with local checkouts (wins over lock)
nimble.paths  — maps resolved packages to on-disk paths for the compiler
```

**Compiler configuration**
```
nim.cfg       — static flags and path additions
config.nims   — project-root NimScript config (processed after nim.cfg)
.nims         — per-file or per-directory NimScript config
```

The two sides interact at one key point: `nimble.paths` (or the paths it encodes) must be visible to the compiler, either by inclusion in `nim.cfg`/`config.nims` or by passing `--NimblePath` on the command line, so that `import packageName` resolves to the correct `.nim` file on disk.

## Processing Order

From https://nim-lang.org/docs/nimc.html#compiler-usage-configuration-files

When the Nim compiler compiles `$project.nim`, configuration files are processed in this order (later files override earlier ones):

1. `$nim/config/nim.cfg` — global Nim installation config (`--skipCfg` to skip)
2. `$XDG_CONFIG_HOME/nim/nim.cfg` or `~/.config/nim/nim.cfg` (POSIX) / `%APPDATA%/nim/nim.cfg` (Windows) — user config (`--skipUserCfg` to skip)
3. `nim.cfg` in each parent directory of the project file, walking up from the project root (`--skipParentCfg` to skip)
4. `$projectDir/nim.cfg` — project-local config (`--skipProjCfg` to skip)
5. `$projectDir/$project.nim.cfg` — project-specific config, named after the project file (`--skipProjCfg` to skip)

NimScript files (`.nims`, `config.nims`) can also be used for configuration and are processed after `nim.cfg` files. Command-line settings have priority over all configuration file settings.

Nimble pre-processes the package graph (`.nimble` + `nimble.lock`) before compilation begins and injects the resolved paths so that step 4/5 can reference them.

## Search Path Handling

When resolving an `import`, Nim checks locations in this order:

1. The **current directory** (directory of the importing file) — checked first, before the global PATH
2. The **global PATH** — directories added via `--path:`, `nim.cfg`, `config.nims`, or `nimble.paths`; if multiple matches exist an ambiguity error is raised, with the first match in PATH winning

Example: given this layout:

```
$lib/x.nim
$lib/bar/x.nim
foo/x.nim
foo/main.nim
other.nim
```

- `main.nim` importing `x` finds `foo/x.nim` first (current directory check)
- `other.nim` importing `x` finds `$lib/x.nim` (first match in PATH; `$lib/bar/x.nim` is also a match but loses)

Run `nim dump` to inspect the active PATH for a project.

### Implications for nimforest

The current directory check means that a bare `import helpers` in `src/foo.nim` will find `src/helpers.nim` without any path configuration — this is the case nimforest already handles. The PATH is only needed for imports that reach outside the importing file's own directory, which in well-structured projects is handled by `srcDir` and `paths` in the `.nimble` file rather than requiring `nim.cfg` parsing.

## `.nimble` Field Reference

From https://nim-lang.github.io/nimble/nimble-reference.html

### `[Package]` — Required

| Field | Description |
|---|---|
| `name` | Package name (not required in NimScript format) |
| `version` | Current version; increment before tagging a release |
| `author` | Author name |
| `description` | Human-readable description |
| `license` | License identifier (e.g. `MIT`) |

### `[Package]` — Optional: Installation filtering

| Field | Description |
|---|---|
| `skipDirs` | Directory names to exclude from installation (comma-separated) |
| `skipFiles` | File names to exclude from installation (comma-separated) |
| `skipExt` | File extensions to exclude, without leading `.` (comma-separated) |
| `installDirs` | Directories to exclusively install; nothing else is installed except these, `installFiles`, `installExt`, the `.nimble` file, and any binary |
| `installFiles` | Files to exclusively install (complements `installDirs` and `installExt`) |
| `installExt` | Extensions to exclusively install (complements `installDirs` and `installFiles`) |

### `[Package]` — Optional: Build configuration

| Field | Description |
|---|---|
| `srcDir` | Directory containing `.nim` source files. **Default:** the directory containing the `.nimble` file (project root) |
| `binDir` | Directory where `nimble build` writes compiled binaries. **Default:** project root |
| `bin` | Comma-separated list of files to build as binaries (no extension needed). Makes this a binary package |
| `namedBin` | Like `bin` but with explicit output names: `name:value`. Overrides duplicates in `bin` |
| `backend` | Compiler backend for `bin` targets: `c`, `cc`, `cpp`, `objc`, or `js`. **Default:** `c` |
| `paths` | Relative paths added to `nimble.paths` and the compiler's search path. Covers the same ground as `--path:` in `nim.cfg` but declared in the package manifest |
| `entryPoints` | Relative paths to `.nim` files used by nimlangserver as project entry points. Useful for test aggregator files such as `tall.nim` |
| `testEntryPoint` | Relative path to the test file containing imported tests (e.g. `tall.nim`). **Default:** `""` (empty; if unset, Nimble discovers test files automatically) |

### Relevance to dependency tree building

For nimforest, the fields that matter are:

- **`srcDir`** — defines the root from which local imports are resolved. If unset, the project root is used. This subsumes the common `nim.cfg` pattern of `--path:"$projectDir/src"`.
- **`paths`** — additional search paths declared at the package level. Reading these from `.nimble` avoids the need to parse `nim.cfg` or `config.nims` for path expansions in most real-world projects.
- **`entryPoints`** — the natural starting nodes for graph traversal; prefer these over `bin` when present.
- **`bin` / `namedBin`** — fallback entry points when `entryPoints` is absent.
